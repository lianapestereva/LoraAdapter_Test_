# Отчёт по проекту и деплою модели

## 1. Краткий отчёт о проделанной работе

На выполнение задания ушло примерно 3 часа: подготовка данных и генерация синтетических примеров, обучение двух LoRA-адаптеров, генерация выходных файлов, проверка результатов и подготовка ответа по vLLM.

Основная сложность — выходные тексты не всегда соответствовали нужному стилю: модель либо недостаточно точно воспроизводила иронично-аналитическую подачу для type1, либо упрощала городской формат для type2. Для решения этой проблемы я дополнила исходные датасеты синтетическими примерами и подобрала гиперпараметры обучения LoRA. Это позволило модели лучше уловить стилевые паттерны, хотя отдельные генерации всё ещё требуют ручной проверки.

### Почему была выбрана модель `Qwen/Qwen2.5-3B-Instruct`?

Для проекта выбрала `Qwen/Qwen2.5-3B-Instruct`, так как она подходит для задачи стилизации и редактирования текста. При относительно небольшом размере модель показывает достаточно хорошие результаты и при этом не требует большого количества видеопамяти. Это позволяет обучать её и использовать для генерации текста без слишком высоких вычислительных затрат.

### Почему я добавила синтетические данные?

Изначально в каждом файле было всего по 25 примеров, чего оказалось недостаточно для полноценного обучения модели. Такого количества данных было мало, чтобы Qwen могла хорошо уловить особенности каждого стиля и научиться воспроизводить характерные паттерны в текстах.

Чтобы улучшить качество обучения, я дополнительно сгенерировала синтетические данные с помощью ИИ. Для каждого файла было создано ещё по 75 примеров, которые дополнили исходные данные. В итоге каждый датасет содержал по 100 примеров.

При генерации дополнительных текстов учитывались особенности двух Telegram-каналов: для @banki_oil — иронично-аналитическая подача, а для @moscowach — динамичный городской новостной стиль с использованием эмодзи.

Такой подход позволил увеличить объём обучающих данных и дать модели больше примеров, по которым она могла усвоить особенности каждого стиля.

### Как настраивалось обучение (Unsloth + SFT)?

Для обучения использовались Unsloth и метод SFT. Unsloth помог ускорить процесс и снизить потребление видеопамяти на GPU Tesla T4 в Kaggle.

Для LoRA были выбраны следующие параметры:
- `r = 16`;
- `lora_alpha = 16`;
- целевые модули: `q, k, v, o, gate, up, down`.

Такая конфигурация позволяет адаптировать модель под нужный стиль, не обучая все её параметры. В результате доля обучаемых параметров составляет примерно 0,96%.

Основные параметры обучения:
- `learning_rate = 1e-4`;
- планировщик learning rate — `cosine`;
- `batch_size = 2`;
- `gradient_accumulation_steps = 2`;
- эффективный размер батча — 4;
- `epochs = 6`, всего около 150 шагов.

Эти настройки использовались для постепенного снижения loss и адаптации модели под заданные стили без чрезмерного увеличения времени обучения.

## 2. Развёртывание модели в продакшене с помощью vLLM

### Условия задачи

Необходимо развернуть модель на сервере с одной видеокартой на 24 GB VRAM, например RTX 3090 или A10G. Сервис должен работать через vLLM и выдерживать нагрузку до 15 одновременных запросов с контекстом до 4096 токенов.

### Вопрос 1. Команда запуска vLLM

Для запуска сервиса можно использовать следующую команду. Она включает поддержку LoRA-адаптеров, чтобы применять разные стили генерации без необходимости загружать отдельную базовую модель для каждого из них.

```bash
python3 -m vllm.entrypoints.openai.api_server \
    --model Qwen/Qwen2.5-3B-Instruct \
    --max-model-len 4096 \
    --gpu-memory-utilization 0.90 \
    --enable-lora \
    --max-loras 2 \
    --max-cpu-loras 4 \
    --lora-modules \
        banki_oil=/path/to/lora_type1 \
        moscowach=/path/to/lora_type2 \
    --port 8000
```

В этой конфигурации используется одна базовая модель `Qwen/Qwen2.5-3B-Instruct` и два LoRA-адаптера: `banki_oil` и `moscowach`. Параметр `--max-loras 2` задаёт максимальное количество адаптеров, которые могут использоваться одновременно на GPU, а `--max-cpu-loras 4` позволяет держать до четырёх адаптеров в системной памяти.

Параметр `--max-model-len 4096` ограничивает максимальную длину последовательности, а `--gpu-memory-utilization 0.90` задаёт долю видеопамяти, которую vLLM может использовать.

### Вопрос 2. Как подобрать `gpu_memory_utilization` и `max_model_len`, чтобы избежать CUDA OOM?

При настройке сервиса важно учитывать не только размер самой модели, но и память, необходимую для LoRA-адаптеров, KV-кэша и работы CUDA. Особенно это актуально при одновременной обработке нескольких запросов с длинным контекстом.

**1. Память под базовую модель**

`Qwen2.5-3B` содержит около 3 миллиардов параметров. Если использовать FP16 или BF16, на каждый параметр требуется примерно 2 байта.

Таким образом, для хранения весов модели потребуется около 6 GB видеопамяти.

**2. Память под LoRA-адаптеры**

Каждый LoRA-адаптер занимает ориентировочно 100–150 MB. Для двух адаптеров потребуется менее 0,5 GB VRAM.

По сравнению с базовой моделью это небольшая часть общей памяти, поэтому использование двух адаптеров не должно существенно увеличивать требования к видеопамяти.

**3. Память под KV-кэш**

При высокой нагрузке значительная часть видеопамяти может расходоваться на KV-кэш, который хранит промежуточные данные для обработки токенов в контексте.

Для оценки объёма KV-кэша на один токен используется формула:

`2 * num_layers * num_kv_heads * head_dim * sizeof(fp16)`

Для рассматриваемой конфигурации расчёт выглядит следующим образом:

`2 * 36 * 8 * 128 * 2 байта ≈ 147,5 KB на токен`

Если одновременно обрабатываются 15 запросов с контекстом по 4096 токенов, общее количество токенов составит:

`15 * 4096 = 61 440 токенов`

Соответственно, для KV-кэша потребуется примерно 9 GB видеопамяти.

**4. Общая оценка потребления видеопамяти**

Суммируем основные составляющие:

- базовая модель — около 6 GB;
- два LoRA-адаптера — менее 0,5 GB;
- KV-кэш — около 9 GB;
- дополнительная память на CUDA и внутренние процессы vLLM — около 2 GB.

Итого получается примерно 17,5 GB VRAM.

На видеокарте с 24 GB памяти параметр `--gpu-memory-utilization 0.90` позволяет vLLM использовать до 21,6 GB. По предварительной оценке, этого достаточно для размещения модели, адаптеров и KV-кэша с некоторым запасом.

При этом фактическое потребление памяти зависит от длины запросов, количества одновременно обрабатываемых последовательностей и настроек самого vLLM. Поэтому после развёртывания стоит проверить работу сервиса под нагрузкой и убедиться, что при пиковом количестве запросов не возникает CUDA OOM.

Параметр `--max-model-len 4096` задаёт максимальную длину последовательности в 4096 токенов и помогает контролировать потребление памяти. Однако сам по себе он не гарантирует, что все 15 запросов смогут одновременно использовать весь контекст: фактическая параллельность будет зависеть от доступного KV-кэша и настроек планировщика vLLM.

В целом конфигурация с `gpu_memory_utilization = 0.90` и `max_model_len = 4096` является разумной отправной точкой для сервера с 24 GB VRAM. Окончательные параметры лучше подтвердить нагрузочным тестированием на целевом оборудовании.
